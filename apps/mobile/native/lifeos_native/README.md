# lifeos_native

Native primitives for the Flutter app. Today: EmbeddingGemma-300M
sentence embedder via `fastembed-rs` + ONNX Runtime, with
auto-generated Dart bindings via `flutter_rust_bridge` (D-1.7c per
`docs/lifeos-shell.md` §6.6).

Scope is intentionally minimal per `lifeos-shell.md` §10: one Rust
crate, public API is one opaque struct + four methods + two free
functions — everything FRB scans lives under `src/api/`. **Do not**
grow this crate beyond the Memory Layer embedder + (future) sync
E2EE / ANN. Anything else stays in Dart.

## Layout

```
Cargo.toml                    # fastembed + ort (download-binaries) + flutter_rust_bridge, release profile tuned for size
src/
  lib.rs                      # `pub mod api;` + `mod frb_generated;`
  api/
    mod.rs                    # `pub mod embedder;`
    embedder.rs               # FRB-visible Rust API (GemmaEmbedder + helpers)
  frb_generated.rs            # AUTO-GENERATED by flutter_rust_bridge_codegen (do not edit)
dist/                         # build outputs (gitignored)
  macos/liblifeos_native.dylib
  ios/LifeosNative.xcframework
  android/<abi>/liblifeos_native.so
```

## Rust API surface (what FRB scans)

```rust
// src/api/embedder.rs
pub fn embedding_dim() -> u32;             // #[frb(sync)] — Dart returns plain int
pub fn embedder_fingerprint() -> String;   // #[frb(sync)]

#[frb(opaque)]
pub struct GemmaEmbedder { /* private */ }

impl GemmaEmbedder {
    pub fn load(model_dir: String) -> Result<GemmaEmbedder>;  // async on Dart
    pub fn dimension(&self) -> u32;                            // #[frb(sync)]
    pub fn fingerprint(&self) -> String;                       // #[frb(sync)]
    pub fn embed(&self, text: String) -> Result<Vec<f32>>;     // async on Dart
}
```

FRB generates the matching Dart class + serialisation at
`apps/mobile/lib/src/rust/api/embedder.dart`. `Result<T, anyhow::Error>`
on the Rust side becomes a Future that throws a Dart exception
carrying the error message.

Higher-level wrapper (implements the project's `Embedder` interface):
`apps/mobile/lib/core/ai/local/embedding/rust_gemma_embedder.dart`.

## Build

**The primary build path is `flutter run` / `flutter build`.**

`apps/mobile/rust_builder/` is a Flutter plugin scaffolded by
`flutter_rust_bridge_codegen integrate`. Its podspec / gradle hooks
invoke **cargokit** (`rust_builder/cargokit/build_pod.sh` etc.) which
runs `cargo build` for the correct target and links/bundles the
resulting library into the Flutter app:

- iOS / macOS: CocoaPods runs the `lifeos_native.podspec` "Run
  Script" build phase → cargokit → cargo
- Android: Gradle applies `cargokit/gradle/plugin.gradle` → cargokit
  → cargo
- Linux / Windows: cargokit CMake module integrates similarly

No manual step required for end-to-end app builds.

### Regenerating FRB Dart bindings

When the Rust API in `src/api/*.rs` changes:

```bash
cd apps/mobile && flutter_rust_bridge_codegen generate
# → regenerates lib/src/rust/{api/*.dart, frb_generated.{dart,io.dart,web.dart}}
# → regenerates native/lifeos_native/src/frb_generated.rs
```

Then `flutter run` rebuilds the native lib automatically.

### Out-of-Flutter build (optional `tool/build-lifeos-native.sh`)

The legacy `tool/build-lifeos-native.sh` is **only needed** when:

- Running `flutter test` on desktop (test harness can't go through
  the plugin loader; tests pass an explicit `libraryPath` from
  `native/lifeos_native/dist/macos/`)
- Producing standalone artefacts (xcframework for cross-repo sharing,
  Rust-only CI smoke build, container image, etc.)

```bash
# Host build (Apple Silicon → aarch64-apple-darwin)
tool/build-lifeos-native.sh macos
# → apps/mobile/native/lifeos_native/dist/macos/liblifeos_native.dylib  (~18 MB)

# Universal macOS
tool/build-lifeos-native.sh macos universal

# iOS xcframework (also produced by cargokit during flutter build ios)
tool/build-lifeos-native.sh ios

# Android (also produced by cargokit during flutter build apk).
# Requires ANDROID_NDK_HOME + cargo-ndk.
tool/build-lifeos-native.sh android
```

> **Build-time download:** the `ort` crate's `download-binaries`
> feature fetches a prebuilt ONNX Runtime native lib from Microsoft
> on first build. The **build machine** needs network access once.
> The final dylib is self-contained — runtime does not need a
> separate `libonnxruntime.{dylib,so}`.

## Model files

The Rust embedder loads `EmbeddingGemma-300M` (INT8 ONNX) from a
user-supplied directory containing five files from
`onnx-community/embeddinggemma-300m-ONNX`:

| File | Purpose |
|---|---|
| `model_int8.onnx`             | Quantised weights (~300 MB) |
| `tokenizer.json`              | Gemma3 tokenizer |
| `config.json`                 | Model architecture config |
| `special_tokens_map.json`     | Tokenizer special tokens |
| `tokenizer_config.json`       | Tokenizer metadata |

Quick download (CLI):

```bash
mkdir -p ~/models/embeddinggemma-300m-ONNX
cd ~/models/embeddinggemma-300m-ONNX

# ONNX INT8 weights (~300 MB)
curl -L -o model_int8.onnx \
  https://huggingface.co/onnx-community/embeddinggemma-300m-ONNX/resolve/main/onnx/model_int8.onnx

# Tokenizer + config (small JSON files)
for f in tokenizer.json config.json special_tokens_map.json tokenizer_config.json; do
  curl -L -o "$f" \
    "https://huggingface.co/onnx-community/embeddinggemma-300m-ONNX/resolve/main/$f"
done
```

## ONNX Runtime (separate download — required)

The crate uses **`ort-load-dynamic`** instead of statically linking
ORT, to dodge the duplicate-symbol issue in ORT's prebuilt static
archives (sub-libs each carry a copy of `onnx-ml.pb.cc.o`, surfacing
as ~756 "duplicate symbol" linker errors when force-loaded into the
Flutter app). The dylib ships separately and is discovered at
runtime via `ORT_DYLIB_PATH`.

Download `libonnxruntime` from the
[Microsoft ONNX Runtime release page](https://github.com/microsoft/onnxruntime/releases)
for your target platform (use the same major version that the `ort`
crate expects — currently 1.20.x):

```bash
# macOS Apple Silicon (~6 MB)
mkdir -p ~/models/onnxruntime
curl -L https://github.com/microsoft/onnxruntime/releases/download/v1.20.1/onnxruntime-osx-arm64-1.20.1.tgz \
  | tar xz -C /tmp/
cp /tmp/onnxruntime-osx-arm64-1.20.1/lib/libonnxruntime.1.20.1.dylib \
   ~/models/onnxruntime/libonnxruntime.dylib
```

For iOS / Android binaries see the corresponding release archives.

The Rust loader also accepts other quantisation variants if you've
already downloaded them: it picks the first match from
`model_int8.onnx → model_quantized.onnx → model_uint8.onnx →
model_q4.onnx → model.onnx`. INT8 is the recommended default
(smallest while keeping cosine quality close to FP32).

## Enabling in the Flutter app

The default embedder is the deterministic `StubEmbedder`. Switch to
the Rust EmbeddingGemma embedder via `--dart-define`:

```bash
# Production path: cargokit bundles liblifeos_native via the
# rust_builder plugin. ORT must be downloaded separately (see above)
# and pointed at via RUST_EMBEDDER_ORT_DYLIB_PATH.
flutter run \
  --dart-define=RUST_EMBEDDER_MODEL_DIR=$HOME/models/embeddinggemma-300m-ONNX \
  --dart-define=RUST_EMBEDDER_ORT_DYLIB_PATH=$HOME/models/onnxruntime/libonnxruntime.dylib
```

For `flutter test` on desktop (test harness doesn't go through the
plugin loader):

```bash
# Build the dylib outside Flutter first.
tool/build-lifeos-native.sh macos

flutter test \
  --dart-define=RUST_EMBEDDER_MODEL_DIR=$HOME/models/embeddinggemma-300m-ONNX \
  --dart-define=RUST_EMBEDDER_ORT_DYLIB_PATH=$HOME/models/onnxruntime/libonnxruntime.dylib \
  --dart-define=RUST_EMBEDDER_LIBRARY_PATH=$PWD/apps/mobile/native/lifeos_native/dist/macos/liblifeos_native.dylib
```

On first boot the [`MemoryRuntime`](../../lib/core/ai/local/memory/memory_runtime.dart)
calls `dropStaleVectors()` automatically — any existing embeddings
made with the stub fingerprint (or a prior model) are dropped, and
the next indexer cycle re-embeds with EmbeddingGemma. No data loss;
typed memory records (events / semantic / episodic / procedural) are
kept intact, only their vectors are recomputed.

If the library or model is missing, the app logs a warning and falls
back to `StubEmbedder`. This is the documented graceful-degradation
path; production builds without the model bytes still boot.

## Why fastembed (vs candle / llama.cpp / raw `ort`)

| Crate | binary size | DX complexity | model format | Notes |
|---|---|---|---|---|
| **fastembed** (chosen) | ~2.5 MB dylib + ~6 MB ORT dylib | low — `embed(vec)` one-liner | ONNX (`UserDefinedEmbeddingModel`) | Simple API, INT8 quant. Uses `ort-load-dynamic` — ORT shipped separately, dodges static-archive dup-symbol issue |
| candle | ~2.4 MB dylib | medium — manual BertModel + pool + normalise | safetensors only | Smaller binary, but no Gemma3-embedding wiring out of box, no GGUF Q8_0 for embedding |
| llama-cpp-2 (GGUF Q8_0) | ~3–5 MB | medium — cmake build, embedding API | GGUF | Right format for "Q8_0" literal, but cmake adds CI friction |
| raw `ort` | similar to fastembed | high — write tokenization + pooling ourselves | ONNX | Lower-level than fastembed; not worth the extra code |

We picked fastembed for **dev simplicity** + the `ort-load-dynamic`
escape hatch keeps our static lib clean. Trade-off: users have to
download `libonnxruntime.dylib` separately (one-time, ~6 MB),
but: ORT auto-selects execution providers (CoreML on macOS / NNAPI
on Android / CUDA where available), and the Rust→Dart `embed()`
surface stays a one-liner.

`lifeos-shell.md` §10 still holds — the FFI surface is the same FRB-
exposed methods, and Memory Layer upper code doesn't know which
crate is underneath.

## Adding new FFI capability

Reasons to expand this crate (per `lifeos-shell.md` §10):

1. **Sync E2EE** — `age` or `libsodium-sys-stable`. Triggered when
   sync v2 has been stable ≥ 1 month (still pending).
2. **ANN** — `usearch-rs` or `hnsw_rs`. Triggered when Memory Layer
   crosses ~50k entries.

Anything else stays in Dart. Do **not** add Drift access, Riverpod
refs, business logic, or wide message dispatch (the AppFlowy
FlowySDK pattern) — those would breach `northstar §1.3`.
